# 数据兼容与安全

## 基线

v4 以 v3 的 SQLite schema v6 为兼容基线，保留 `resumes`、`applications`、`materials`、`profile`、`job_targets`、`application_attachments`、`job_tasks`、`interviews` 八张业务表。

## 迁移原则

1. 开发阶段默认使用独立目录，绝不自动打开真实 v3 数据库。
2. 用户在空白 v4 中通过 Windows 文件夹选择器或手动路径选择包含 `data.db` 的 v3 数据目录；检查通过并明确确认后，先创建带时间戳的 v4 备份，再把 v3 数据库快照和受管文件复制到 v4 数据目录。
3. 不对原 v3 数据库原地升级。
4. 新结构只通过版本化迁移增加；发现高于程序支持版本的数据库时拒绝启动。
5. 所有导入先在临时数据库中校验，成功后再进行原子替换。

Python v3 与 v4 的同名表不要求列数完全一致。导入时按列名取交集，并按 v4
目标列顺序显式写入；v4 新增列使用 schema 默认值。这样可兼容例如 v3
`resumes` 的 10 列与 v4 的 12 列，避免 `INSERT ... SELECT *` 因列数变化失败。
如果旧表缺少的目标列既是必填项又没有默认值，导入会在写入前明确拒绝，整次
事务回滚，不会留下半套数据。

启动时只进行旧目录候选探测，不会自动导入，也不会与 v3 共用数据库。用户可以覆盖自动探测结果，手动选择任意本机 v3 数据目录或直接填写 `data.db` 路径。目标已有任一真实业务记录时，一键导入会拒绝执行，防止两套数据意外混合；发布包的虚构演示数据必须由用户明确清除后再迁移。

## 时间

数据库写入使用带时区的 RFC 3339 时间；读取 v3 无时区时间时按本机时区解释。网页展示始终转换为用户本地时间，避免此前 UTC 与北京时间混淆。
